# Известные баги и нестыковки бизнес-логики

Аудит от 2026-08-19. Найдены противоречия, нестыковки в бизнес-логике и неучтённые
корнер-кейсы. Проверены `assets/{store,sync,calc,xlsx-import}.js`, логика
движений/переносов/аналитики/форм в `assets/app.js` и `backend/main.go`. Находки
перекрёстно подтверждены тремя независимыми проходами и ручной сверкой. Сгруппировано
по серьёзности, с `файл:строка` и сценарием воспроизведения.

---

## CRITICAL — ломают ядро (синк / инвариант остатка)

### C1. Правка во время «летящего» синка теряется навсегда
`sync.js:161-179`. Снимок `saveSyncState(snapshotFromRecords(exportRecords()))` берётся
ПОСЛЕ `await postSync`. Запись, добавленная во время сетевого раунд-трипа, попадает в
новый снимок с её `updatedAt`, поэтому следующий `computePush` считает её уже
синхронизированной (`sync.js:84`) и не отправляет никогда (движения иммутабельны —
второго шанса нет).
**Фикс:** строить снимок из `local` (снятого до await) + применённых серверных эхо, а
не из post-await состояния.

### C2. После пула серверных изменений UI не перерисовывается
`app.js:1697,1706,1938,1975`. `syncNow()` возвращает `{ok, seq, pushed}`, но ВСЕ
вызывающие проверяют `r.changed` (такого поля нет) → `render()` не вызывается. Плюс на
`store.onChange` висит только `scheduleAutoSync`, нет рендер-листенера. Данные с других
устройств приходят и сохраняются, но экран показывает старое до ручного действия.
`pullReplace` рендерит безусловно — поэтому баг незаметен только там.

### C3. `now()` не переживает перезагрузку → легитимная правка отклоняется LWW
`store.js:23-28`. `lastStamp` in-memory. Пакетные `addMovement` (импорт/seed) в одну мс
уводят `lastStamp` выше wall-clock. Перезагрузка → `lastStamp=0`. Правка такой записи
получает `updatedAt < сохранённого`, сервер `apply` (`main.go:167` `<=` → continue)
отклоняет, `applyServerRecords` (`store.js:534`) принимает старую версию и откатывает
правку пользователя. Монотонность есть только внутри сессии.

### C4. Тай-брейк LWW расходится клиент/сервер → перманентный split-brain
`store.js:534` vs `main.go:167`. Нет тай-брейка по `id`. При равных `updatedAt` (два
устройства, одна мс после перезагрузки) сервер оставляет инкумбента, клиент — своё;
`snapshot[id]===updatedAt` → запись больше никогда не пушится. Устройства расходятся
навсегда без сходимости.

### C5. `deleteMovement` не защищает transfer-пары → фантомный остаток
`store.js:448-455`, `app.js:1171-1174`. Кнопка удаления рисуется для ЛЮБОГО движения
(для transfer скрыт только ✎). `updateMovement` осознанно блокирует transfer
(`store.js:463`), а `deleteMovement` — нет. Удаление одной половины переноса: остаток
исходного этажа скачет +qty, целевой не меняется. Защиту надо перенести в store.

## HIGH

### H1. Отрицательный остаток через удаление/правку прихода
`store.js:448`, `app.js:1388-1397`. Guard «не уходить в минус» стоит только при создании
расхода (`app.js:1348`) и правке расхода (под `if(!isIn)`, `app.js:1392`). Удалить приход
или уменьшить приход-запись → `stockOf` уходит в минус без ошибки. Нарушает заявленный
инвариант (`app.js:1347`).

### H2. Правка движения на неактивном этаже молча не открывается
`app.js:1369`. `sheetEditMovement` ищет через `movementsForItem(itemId)` (дефолт =
активный этаж), но карточка в режиме «Все этажи» рисует ✎ для движений всех этажей
(`app.js:1211-1213`). `find` → undefined → `return` без тоста. При этом удаление того же
движения работает (сканирует все) — рассогласование edit/delete. Математика guard'а на
`app.js:1393` уже использует `m.floorId`, т.е. писалось под кросс-этажную правку —
противоречие внутри функции.

### H3. Подпись этажа не совпадает с данными в отчёте/сводке
`app.js:803`+`833`. Отчёт считает по `analyticsFloor` (масштаб аналитики), а подпись
жёстко пишет `этаж «${getActiveFloor().name}»`. При масштабе «Все этажи»/«Этаж 2» и
активном «Этаж 1» цифры и подпись противоречат друг другу.

### H4. `persist()` без try/catch
`store.js:126-129`. `load()` защищён, `persist` — нет. QuotaExceeded → мутация в памяти
прошла, на диск не легла, `notifyChange` не вызван → тихий рассинхрон память/диск +
падение UI-действия.

### H5. Импорт xlsx ↔ синк: воскрешение старых данных дублями
`store.js:583-649`, `sync.js:157`. `importFromParsed` делает `state=defaultState()` с
новыми id, но не координируется с in-flight синком. Серверная дельта (старые id) после
import сливается обратно (`applyServerRecords` push отсутствующих id) → «заменённые»
данные возвращаются рядом с импортированными. UI обещал замену — синк её отменяет.

## MEDIUM

### M1. Кросс-девайсные «сироты» (нет ссылочной целостности в merge)
`store.js:523-539`. Живой товар в удалённой категории (A удалил категорию в `t`, B правил
товар в `t2>t`); живое движение на удалённом этаже/товаре. `ensureFloors` переназначает
`floorId` только если он пустой (`store.js:82`) — сирота остаётся висеть. Товар-сирота
попадает в список заказа (`allItems()`), но исчезает из «Средних по категориям»
(`app.js:731`) — «есть» и «нет» на одном экране.

### M2. Delete-vs-update воскрешение
`store.js:534`. B переименовал товар (`t2>t`), A удалил (`t`). Товар воскресает, но
движения остались тумбстоунами → товар с нулевым остатком.

### M3. Σ(по этажам) ≠ «Все этажи»
`store.js:188-198`. При `floorId==null` суммируются движения всех этажей, включая
движения на удалённом (через синк/import) этаже; поэтажный обзор итерирует только
`floors()` (живые). Суммы расходятся.

### M4. Настройки сливаются одной записью целиком
`store.js:540-546`. A меняет `windowDays`, B — `workingDaysOnly`: побеждает одна запись,
правка второго теряется (нет пофилдового merge).

### M5. Нет валидации `windowDays`/`workingDays`/`minStock`
`store.js:300-304`. `windowDays=0` → `windowStart=asOf+1` (окно в будущем, `calc.js:141`)
→ средние молча 0. Отрицательный `minStock` пропускается в create/edit-item
(`app.js:1088,1633`), но блокируется в edit-min (`app.js:1588`).

### M6. `workingDaysOnly`: числитель по всем дням, знаменатель по рабочим
`calc.js:146-156`. `sumConsumption` не фильтрует по рабочим дням, делитель
`countWorkingDays`. Расход в выходной при `workingDaysOnly` завышает средний
расход/срочность/заказ (напр. `workingDays=[6]`, расход каждый день → делёж на ~4 → ×7
завышение).

### M7. После wipe/пустых этажей каждое устройство создаёт свой «Этаж 1»
`store.js:72-80` (в `applyServerRecords:548`, `replaceFromServerRecords:578`). Разные uid
→ дубликаты этажей после синка. Аналогично при независимом импорте на двух устройствах.

### M8. Дубли имён в ручных формах
`store.js:241,308,358`. Импортёр дедупит категории/товары по нормализованному имени
(`xlsx-import.js:285,338`), а ручной ввод создаёт две «Соль»/два «Этаж 1» (чипы
неразличимы). Рассогласование ручного и импортного путей.

### M9. `updateMovement`/`deleteMovement` no-op, но UI рапортует успех
`app.js:1398-1401`. Фоновый merge тумбстоунит запись → `updateMovement` возвращает
`null`, UI всё равно тостит «Движение изменено».

### M10. Удаление движения без подтверждения
`app.js:1299-1305`. Товар/категория/этаж — через `confirm()`, движение — сразу. Плюс
(см. C5) может порушить перенос. Деструктивно, без undo.

### M11. xlsx: один товар в двух этаж-секциях листа → потеря данных
`xlsx-import.js:338,353-367`. Ключ товара без этажа; при повторе перезаписываются
moves/stock/floor (`>=`). Модель товара имеет одно поле `floor` (`xlsx-import.js:387`) —
структурно не может хранить один товар на двух этажах, хотя разбиение по этажам внутри
листа — штатная фича.

### M12. Импорт принимает отрицательный/NaN остаток
`xlsx-import.js:330,359`, `store.js:619`. Отрицательная «Итого остаток» или мусорная
ячейка (→NaN→0) при наличии приходов даёт отрицательный on-hand, который остальное
приложение считает невозможным.

## LOW

- **`recommendedOrder` округляет вверх дробные единицы** — `calc.js:188-192`. 2.5 кг →
  заказ 3.
- **Задним числом расход/правка обходят guard на исторический минус** — guard проверяет
  текущий общий остаток, не `stockAsOf(date)`; на промежуточных датах баланс может уйти в
  минус.
- **`version` не используется, пути миграции по версии нет** — `store.js:8,101-124`.
- **Повреждённый JSON → тихий полный сброс и перезапись** — `store.js:88-98`.
- **Sync-конфиг сохраняется до успешного теста** — `app.js:1687-1694`.
- **Переносы всегда датой «сегодня»** — `app.js:1524` (в отличие от
  прихода/расхода/инвентаризации).
- **`order` = длина массива → коллизии, недетерминированный порядок между устройствами**
  — `store.js:247,312,365`.
- **xlsx: нет ограничения размера/отмены; регистр отображаемого имени зависит от порядка
  строк** — `xlsx-import.js:31-73,328`.
- **Пустое имя категории/товара без фолбэка** — `store.js:308,358` (у этажа фолбэк
  `|| "Этаж"` есть, у категории/товара нет); `transferStock` не проверяет существование
  товара — `store.js:285`.

## Корректно обработано (проверено, не баги)

Поиск через `.includes()` по lower-case (пустой запрос/регистр/regex-спецсимволы
безопасны); `esc()` от HTML-инъекций; удаление активного этажа переставляет
`activeFloorId` и сбрасывает `analyticsFloor`; последний этаж удалить нельзя; повторный
импорт локально заменяет, а не копит; `round1/round2` нормализуют -0; guard на минус при
создании расхода и переносе.

## Предлагаемый порядок исправления

1. **Синк-корректность (C1–C4)** — самое опасное, тихая потеря/откат данных и split-brain.
   Требует: снимок из pre-await local; persist `lastStamp`; тай-брейк по id в клиенте и
   сервере; поле `changed` из `syncNow` + рендер-листенер.
2. **Инвариант остатка (C5, H1, H2)** — guard transfer в `deleteMovement`, guard минуса
   при удалении/правке прихода, кросс-этажный lookup в `sheetEditMovement`.
3. **UI-нестыковки (H3, M9, M10)** — правильная подпись этажа, реакция на no-op, confirm
   на удаление.
4. **Валидация/дедуп (M5, M6, M8, M11, M12)** + тесты
   (`tests/{sync,store,calc}.test.mjs`, `backend/main_test.go`) на каждый merge/edge — по
   правилам репозитория «фича не готова без тестов».
